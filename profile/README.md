<p>关于"要不要给每个号配一条独立出口"，争论通常停在各说各话。与其争，不如做一次对照：同一批任务、同一台机器、同一份配置模板，只让出口这一个变量不同，跑两周看数据。这篇记录的就是这样一次实验——A 组六个号共用两条共享出口，B 组六个号各配一条独享原生家宽出口，其余条件全部拉平，最后给指标表、差异归因和适用边界。</p>

<h2>一、实验设计：两组各六个号</h2>
<p>两组各六个号，来自同一批注册时间相近的账号，注册地区同为美西。任务完全相同：每天上午登录、发三轮对话、晚上再登录一次。观察期十四天。</p>

<h3>为什么用同批次账号</h3>
<p>账号的历史状态是最大的干扰变量。用注册时间相近、注册地区相同、此前都没有异常记录的号，能把"号本身的问题"降到最低。如果一组全是老号、另一组全是新号，任何差异都无法归因。</p>
<h3>样本量的局限要先说清</h3>
<p>六对六的样本量只能看趋势，不能做统计结论。这次实验的价值在于把现象暴露出来，而不是证明因果。要更可靠，样本至少要三四十对，且观察期覆盖一个月。</p>

<h2>二、变量控制：只让出口不同</h2>
<p>控制变量听起来简单，做起来最容易漏。这次严格拉平了五项：同一台机器、同一个浏览器版本、同一份配置模板、同样的操作时段、同样的对话内容。</p>
<p>配置模板拉平的方式是：先做一份只对齐时区和语言的空白母版，两组都从这份母版克隆，唯一差异是代理指向不同的出口。这样会话层的所有条件完全一致，差异只能来自网络层。</p>
<h3>时区怎么处理才不制造新变量</h3>
<p>两组账号都在美西，时区统一设成太平洋时间，出口也都在美西。如果 A 组有号落到别的城市，时区跟着改，那就多了一个变量。所以实验前先确认所有出口的注册城市一致。</p>
<h3>操作节奏要去掉人为差异</h3>
<p>两组用同一个脚本控制节奏：登录间隔、对话轮次、每次停留时长都写死在脚本里。人工操作容易在状态好的时候多点几次，这种偏差会污染数据，尤其在样本量小的时候。</p>

<h2>三、观测指标与记录方式</h2>
<p>指标定四个：登录是否出现验证页、单次登录耗时、对话首字响应、当日是否掉线。四个都能自动记录，不依赖主观判断。</p>
<p>记录方式是每条操作写一行日志：时间、账号编号、组别、耗时、是否出现验证、错误码。日志用同一个格式，最后按组汇总，中位数和九十分位一起看。</p>

<h3>为什么把验证页单独拎出来</h3>
<p>它是所有指标里最接近"平台态度"的一个。耗时和掉线可能受本地网络影响，验证页则基本由环境一致性决定。这一项的差异最能说明问题。</p>
<h3>错误码要原样记录</h3>
<p>不要只记"失败"，要记原始错误码和状态码。302 跳验证、403 拒绝、504 超时是完全不同的三件事，混在一起统计等于没统计。日志里留原值，事后才能分类。</p>

<h2>四、两周数据与差异来源</h2>
<p>十四天累计下来，两组的差距集中在验证页和晚间响应两项，白天的登录耗时差距不大。这个分布本身就说明问题：共享出口的问题不在带宽，在晚间拥塞和同址干扰。</p>

<h3>验证页的时间分布说明了什么</h3>
<p>A 组的十一次验证里，有八次落在晚上八点到十一点。这个时段正是家庭宽带最拥挤的时候，共享出口的同址其他用户也在活跃，链路质量下降。B 组同一时段只有一次，且发生在某条线刚启用的第一天。</p>
<h3>同址干扰比带宽更容易暴露</h3>
<p>A 组两条出口各挂三个号，其中一个号在第七天触发了验证后，同址另外两个号在两天内也各出现一次。这种时间上的连锁，是共享出口最难避免的部分，也是独享出口的核心价值。</p>

<h2>五、结论与适用边界</h2>
<p>结论有三条：独享出口对验证页的抑制效果明确；对白天登录速度的提升有限；对晚间高峰的稳定性提升最大。也就是说，独享不是"更快"，而是"更平"。</p>
<p>边界也要说清。这次实验里，B 组用的是原生家宽出口，如果换成机房属性的独享地址，验证页未必能降到同样的水平——出口属性比独享与否更根本。两者是叠加关系，不是替代关系。</p>
<h3>什么规模适合一号一条</h3>
<p>号的价值高、长期挂着、有人在夜里不值守的，适合。号是短期测试性质、随时能重开的，共享出口加严格的分组也能凑合，但要接受晚间的不稳定。</p>
<h3>实验结论怎么用到自己身上</h3>
<p>照抄结论没用，照抄方法有用。用六个号跑一周，只改出口这一个变量，记录四个指标，你得到的结论比任何评测都贴合自己的业务。成本只是两条线路的差价和一周的观察时间。</p>

<h2>常见问答</h2>
<h3>实验结果能不能直接推广到二十个号？</h3>
<p>答：趋势可以，比例不能。号数增加后，共享出口的同址干扰会非线性放大，独享的优势更明显；但同时线路数量增加，池子质量变得更重要，撞车风险会上升。</p>
<h3>B 组的验证页为什么没有降到零？</h3>
<p>答：验证页不完全由出口决定，还受账号历史、操作节奏、设备状态影响。降到零既不现实也不必要，把比例压到一成以下、并且不在同一时段集中出现，就算达标。</p>
<h3>只改出口、不改浏览器配置，也会有这个效果吗？</h3>
<p>答：会有一部分，但会打折扣。出口解决网络层，配置解决会话层，两层都要一致。这次实验两组配置相同，所以测出的是纯粹的网络层差异。</p>
<h3>十四天够不够？</h3>
<p>答：够看趋势，不够看长期。长期问题通常在第三到第六周出现，比如地址被标记后的连带影响。如果有条件，观察期拉到一个半月更稳妥。</p>
